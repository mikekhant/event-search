05Project Charter

Objective

Every day at 8:00am Pacific, deliver a digest of up to 10 new upcoming events that match the sponsor's professional and personal interests, each with a working sign-up link, at a low daily token cost.

Interest profile

  • Professional: networking events in AI, technology and consulting; UC Irvine events from the Paul Merage School of Business and the School of Information and Computer Sciences (ICS).
  • Personal: golf, pickleball, raves, hiking, book clubs, workout and HIIT classes.
  • Where: within 20 miles of Irvine for Monday to Friday events; from Los Angeles to San Diego for Saturday and Sunday events; online events any day.
  • When and price: starts within the next 14 days; $50 or less per event.

Success criteria

  1. On time: the digest is delivered by 8:30am America/Los_Angeles on 7 of 7 days in the acceptance week.
  2. Complete entries: every event shows title, date and time, location, price, interest tag and a sign-up link. 100% of sampled links open that event's registration page.
  3. Filters hold: 100% of listed events start within 14 days, cost $50 or less, and meet the distance rule for their day of week.
  4. No repeats: zero events appear in more than one digest, and zero declined events reappear.
  5. Volume: up to 10 events per day, ranked by fit. When fewer new events qualify, the digest lists fewer and says so.
  6. Coverage: every interest topic is searched at least twice in the acceptance week.
  7. Cost: every daily run stays inside the per-run cap set at Gate 2.
  8. Notice: a push notification goes out on days with new events, and a one-line note is logged on days with none.

Scope in

  • Interest profile and filter rules.
  • A scheduled task that runs daily at 8:00am America/Los_Angeles.
  • Searching Luma and the wider web (for example Eventbrite, Meetup and UC Irvine event pages).
  • A running Event Digest doc in the Event Search project.
  • A log of events already shown or declined.
  • Calendar events created in this chat when the sponsor asks, after signing up.

Scope out

  • Registering, paying or signing up for anything on the sponsor's behalf.
  • Adding calendar events without being asked.
  • Emailing or contacting organizers, or posting anywhere.
  • Logging in to event accounts.
  • Events over $50 or more than 14 days away.

Constraints

  • Daily token use must stay low. Build usage is unlimited.
  • Tools: web search and public event pages. No Luma connector was found, so Luma is covered through its public pages.
  • The agent never signs up, pays or contacts anyone.

Assumptions

  • Unverified: a scheduled run can read and write the project doc that holds the digest and the log. Test blocked on D-02. Fallback: a Google Drive doc.
  • Verified Nov 20 from the CoS chat: public Luma event pages can be found by search and read. Search returns many past events, and Luma calendar pages omit dates, so each candidate page must be opened to confirm its date.
  • An event is shown once and never again, whether or not the sponsor declined it. This covers the "do not show declined events" rule.
  • Price means the listed ticket price before fees.
  • Distance is judged by the event's city relative to Irvine, not by drive time.
  • Weekend range runs from Los Angeles in the north to San Diego in the south.
  • Ten per day is a ceiling. The digest is never padded with poor matches.

Stakeholders

  • Sponsor: sets direction, approves gates, marks declines, signs up for events.
  • CoS: plans, builds, verifies, reports.
  • Reviewer agent: independent check of early digests.

Top 5 risks

  1. The daily run cannot remember past events, so repeats appear. Response: test persistence before building; fall back to a Google Drive doc.
  2. Daily cost runs high with 11 interest topics. Response: rotate topics across the week, cap searches and page reads, use a lighter model.
  3. Too few new qualifying events to fill 10 a day. Response: list fewer rather than pad; add sources if the gap persists.
  4. Wrong details or dead links taken from search snippets. Response: the run opens each event page before listing it; the Reviewer samples links.
  5. Event sites block automated reading. Response: use alternate sources and flag any source that could not be read in that day's digest.

Daily run design

  • Topic rotation: each run covers 4 or 5 of the 11 topics, so every topic is searched at least 3 times a week. AI, technology and consulting networking runs most days.
  • Sources first: the run reads a fixed list of listing pages before it uses open search, because open search returns many past events.
  • Run limits: up to 8 searches and 15 page reads per run. These guard cost and are not a project budget.
  • Model: the CoS cannot choose the model for a scheduled task from this chat. It runs on whatever the task's settings use.

11Lessons learned

  • Test scheduled-task permissions before planning around them. The first attempt to create one was blocked.
  • The template refers to a Part B onboarding template that was not included in the intake.
  • The template assumes a multi-agent team. For a size S project, a lean-team option at intake saves a planning round.
